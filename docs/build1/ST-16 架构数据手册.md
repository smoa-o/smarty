# ST-16 架构数据手册

## 引言

本文档描述了围绕五级有序流水线构建的CPU内核的微架构和内部通信协议，该流水线由集中式控制单元 ( *CU* ) 控制。
*CU* 通过短四次握手协议逐步协调管道进展，并协调组件内通信。

*CU* 充当流水线主控器，按顺序驱动每个阶段（ *Fetch* -> *Pre-decode* -> *Microcode-sequencer* ->
*Execute* -> *Retire* ) 。在下一阶段派遣之前，每个阶段都会向 *CU* 报告完成情况。 *CU* 通过与内部组件
的短四回声握手来处理内存映射访问和其他服务请求。

设计目标：

- 确定性定时-按顺序流水线，无投机性执行
- 集中控制-CU拥有管道调度和通信仲裁
- 可靠的芯片内通信-具有显式完成确认的四路握手

## 流水线架构

### 五段式架构

*CU* 充当流水线主控器，按顺序驱动每个阶段（ *Fetch* -> *Pre-decode* -> *Microcode-sequencer* ->
*Execute* -> *Retire* ) 。在下一阶段派遣之前，每个阶段都会向 *CU* 报告完成情况。 *CU* 通过与内部组件
的短四回声握手来处理内存映射访问和其他服务请求。

所有服务请求遵循同一模型：请求阶段向 CU 提交请求并等待完成。
CU 仲裁所有访问——无论目标是存储器、寄存器、地址单元还是 ALU——
并通过短四次回响协议返回结果。任何流水线阶段均不直接访问
硬件资源。

#### Fetch（取指）

Fetch 负责从 IMEM 中取回指令并维护指令指针（cfg.ip）。
每个取指周期包含三个步骤：

1. 读指针 — 发送 RRG 请求读取 cfg.ip，获取当前取指地址
2. 取指令 — 向 CU 发送 IMEMRD 请求，CU 通过短四次回响协议
   完成存储器访问
3. 更新指针 — 发送 WRG 请求写回更新后的指令指针
   （顺序递增或分支目标）

所有寄存器和存储器访问均通过服务请求由 CU 中转；
Fetch 不直接访问 IMEM 或寄存器文件。

关键输出：指令字

##### 服务请求

| 类别 | 请求 | 方向 | 目标 | 描述 |
| ---- | -----|------|------|------|
| 寄存器 | RRG | 读 | cfg.ip | 读取当前指令指针 |
| 寄存器 | WRG | 写 | cfg.ip | 更新指令指针 |
| 存储器 | IMEMRD | 读 | IMEM | 取指令字 |

#### Pre-decode（预译码）

Pre-decode 接收 Fetch 阶段输出的指令字，对其进行初步格式化解析，
提取出操作码类别并将指令分解为后续阶段可用的字段。
本质上它只是一个格式化层，不执行复杂逻辑。

每个预译码周期包含以下步骤：

1. 读取输入 — 从上一级流水线寄存器（RBF）读取 Fetch 输出的
   原始指令字
2. 格式解析 — 识别指令格式、提取操作码和操作数布局
3. 输出微码 — 将解析结果输出为微码条目供 uSeq 阶段展开

Pre-decode 不直接访问存储器或寄存器文件；唯一的外部请求是
读取流水线缓冲区的 RBF 请求。

关键输出：微码条目（microcodes）

##### 服务请求

| 类别 | 请求 | 方向 | 目标 | 描述 |
|------|------|------|------|------|
| 缓冲区 | RBF | 读 | 流水线寄存器 | 读取上一级输出（Fetch 的指令字） |

#### Microcode-sequencer (uSeq)

uSeq 接收 Pre-decode 输出的微码条目，将其序列化为可执行的微操作
（μop）流，逐条分发给 Execute 阶段。

每个 uSeq 周期包含以下步骤：

1. 读取输入 — RBF 请求读取 PD 输出的微码条目
2. 序列展开 — 将微码条目展开为 μop 序列（查微码存储或
   直接顺序发射，取决于指令复杂度）
3. 逐条分发 — 将 μop 逐条交给 Execute 阶段执行

uSeq 本身不执行运算，也不直接访问数据通路。它只负责指令到
微操作的翻译和调度。唯一的外部请求是读取流水线缓冲区的
RBF 请求。

关键输出：μop 序列

##### 服务请求

| 类别 | 请求 | 方向 | 目标 | 描述 |
|------|------|------|------|------|
| 缓冲区 | RBF | 读 | 流水线寄存器 | 读取上一级输出（PD 的微码条目） |

#### Execute

Execute 是流水线中请求最密集的阶段。它从 uSeq 接收 μop，
驱动 ALU 完成运算，并通过 CU 发起各类服务请求来完成
地址操作、寄存器读写和数据通路交互。

每个 Execute 周期包含以下步骤：

1. 读取输入 — RBF 请求读取 uSeq 输出的 μop
2. 地址操作 — RAD/WAD 请求进行地址计算（基址读取、
   有效地址写入等）
3. 寄存器操作 — RRG/WRG 请求读写通用寄存器或配置寄存器
4. 执行运算 — rALU 请求驱动 ALU 完成算术/逻辑运算
5. 输出结果 — 将运算结果传递给 Retire 阶段

Execute 是所有数据通路操作的实际执行者；除 RBF 外，
所有请求均通过 CU 中转。

关键输出：运算结果（数据 + 状态标志）

##### 服务请求

| 类别 | 请求 | 方向 | 目标 | 描述 |
|------|------|------|------|------|
| 缓冲区 | RBF | 读 | 流水线寄存器 | 读取上一级输出（uSeq 的 μop） |
| 地址 | RAD | 读 | 地址寄存器/单元 | 读取基地址或索引 |
| 地址 | WAD | 写 | 地址寄存器/单元 | 写入有效地址或计算结果 |
| 寄存器 | RRG | 读 | 寄存器文件 | 读取源操作数 |
| 寄存器 | WRG | 写 | 寄存器文件 | 写回运算结果 |
| 运算 | rALU | 执行 | ALU | 驱动 ALU 完成算术/逻辑运算 |

#### Retire

Retire 是流水线的最后阶段，负责检查执行结果、确认指令提交的
合法性，并在异常发生时触发恢复流程。

每个 Retire 周期包含以下步骤：

1. 读取输入 — RBF 请求读取 Execute 输出的运算结果
2. 异常检查 — 检查 fault 状态（由 Execute 或 CU 标记）
3a. 无异常 — 确认指令正常完成，回报 CU
3b. 有异常 — 触发 RST 流程，清理流水线状态
4. 状态回写 — RRG/RAD 请求读取相关状态信息，
    必要时写回恢复上下文

Retire 不直接写回运算结果（Execute 已完成），它的职责是
"收尾与裁决"：确认一切正常则放行，发现问题则介入恢复。

关键输出：完成确认 / 异常信号

##### 服务请求

| 类别 | 请求 | 方向 | 目标 | 描述 |
|------|------|------|------|------|
| 缓冲区 | RBF | 读 | 流水线寄存器 | 读取上一级输出（Execute 的运算结果） |
| 寄存器 | RRG | 读 | 寄存器文件 | 读取状态/配置信息用于异常判断 |
| 地址 | RAD | 读 | 地址寄存器/单元 | 读取异常现场地址信息 |

#### 错误分级与 RST

架构中错误分为两级：

- **可恢复错误** — 记录到 fault 状态寄存器，由 Retire 阶段
  检查并裁决后续处理（重试或软件介入）
- **硬件 Fatal 错误** — 任何阶段检测到不可恢复的硬件异常时
  直接拉 RST 信号复位整条流水线，不经过 CU 服务请求流程

RST 是硬连线控制信号，优先级高于所有协议握手。
触发后流水线立即清空，所有阶段回到初始状态，同时硬件复位。

### 脚注

Fetch 和 Pre-decode 可为了性能选择性地融合为同一个流水线级，融合后名称仍保留为"Fetch"。
在融合模式下，格式解析在取指完成后于同一级内立即执行，流水线序列中不再出现独立的 Pre-decode 级。

## 通信协议

### 引言

本架构定义了三种通信协议，按参与方数量和使用场景区分：

| 协议 | 参与方 | 别名 | 状态 |
|------|--------|------|------|
| Short Four-Echo | 两方 | — | 已实现 |
| Three-Party Forwarding | 三方（全程转发） | 握发离 | 已实现 |
| Three-Party Direct | 三方（引见后退） | 握离发 | 已实现 |
| Long Four-Echo | 两方（片外） | — | 预留 |

符号约定：

| 符号 | 含义 |
|------|------|
| `->` / `<-` | A <-> B |
| `->>` / `<<-` | A <-> C |
| `-!>` / `<!-` | B <-> C |

角色定义：
- A: Caller（调用方）
- B: Forwarder（转发方，即 CU）
- C: Callee（被调用方）

### 短四步回响

两方协议，用于内部组件与 CU 之间的直接通信。

流程：syn -> ack -> fin&data -> cln

正常时序：

```
Caller (A)          Forwarder (B)

|                    |
|-syn--------------->|
|<--------------ack--|
|                    |
|<-------fin&data----|
|                    |
|----cln------------>|
|<--------------ack--|
```

异常时序：

- 超时：B 未在限定周期内回 ack -> A 重发 syn 或触发 TMOUT
- 失败：B 回 ack -> A 终止当前请求

### Three-Party Four-Echo

三方协议，用于调用方通过 CU 与被调用方通信。包含两个变体。

#### Forwarding Variant (握发离)

B 全程参与每一拍数据转发。流程分为四阶段：握 -> 发 -> 离。

```
Phase 1: 建立连接

A -syn> B
B <ack- A
B -syn!> C
C <!ack- B

Phase 2: 数据传输（A->B->C）

A -snd> B
B <ack- A
B -snd!> C
C <!ack- B

Phase 3: 完成返回（C->B->A）

C -gms!> B          (Get Message)
B <!ack- C
C <!fin&data- B
B -ack!> C
B <ack&data- A
A -ack> B

Phase 4: 清理

A -ack+cln> B
B <ack- A
B -cln!> C
C <!ack- B
B <ack- A
```

注意：直接变体中 B 不参与 Phase 2–4，仅负责初始引见。

### Long Four-Echo

片外通信协议，用于 CPU 与外部设备之间的交互。
基本流程与 Short Four-Echo 一致，但 ack 阶段增加了
超时与忙状态反馈机制。
流程：syn -> ack(含状态) -> fin&data -> cln

#### 正常时序

A (CPU)            C (External Device)
    |                    |
    |-syn--------------->|
    |<--------------ack--|  (ready, 正在获取数据)
    |                    |
    |<-------fin&data----|  (完成，数据就绪)
    |                    |
    |----cln------------>|  (清除数据)
    |<--------------ack--|

#### ACK 阶段状态响应

| 响应 | 含义 | 条件 | 处理 |
|------|------|------|------|
| ack | 已准备好，正在获取 | 设备就绪 | 正常进入 fin&data |
| BSY | 忙，未准备好 | 收到消息但设备忙 | 重试等待 |
| LBSY | 轻度过忙 | 连续 10 次或 100 周期内未回复 | 延迟过高，预期 35clk/次 |
| TBSY | 重度过忙 | 连续 5 次或 135 周期内未回复 | 延迟过高，预期 70clk/次 |
| TBSY (直接) | 直接结束 | 设备完全不可用 | 立即终止对话，清除数据 |

#### 超时规则

- BSY：设备未就绪，A 继续等待，设备持续返回 BSY
- LBSY：连续 10 次 BSY 或 100 周期内无回复 -> 返回 LBSY，
  表示延迟过高。预期恢复时间 35clk/次。A 可选择继续等待或放弃
- TBSY：连续 5 次 LBSY 或 135 周期内无回复 -> 返回 TBSY，
  表示设备严重过载。预期恢复时间 70clk/次。
  A 收到 TBSY 后直接终止对话，清除数据

#### 清理阶段

-cln> 表示"弄好了，你可以清除数据了"。
如果设备仍未就绪，可继续返回 BSY/LBSY（不发 TBSY），
但延迟过高时直接发 TBSY 并立即清除数据。

## 异常与恢复

### 错误分级

| Level | Type | Handling |
|-------|------|----------|
| Recoverable | 可记录 fault | 写状态寄存器，Retire 裁决 |
| Fatal | 硬件错误 (INVSTP, TMOUT, ...) | 直接拉 RST |

### 超时处理

- 短四步回响：超时 -> TMOUT 信号 -> RST 或重试（取决于配置）
- 三方协议：转发方超时 -> 向调用方返回失败
- 长四步回响：BSY/LBSY/TBSY 分级响应

### 重试策略

| Scenario | Retry Count | Action on Exhaust |
|----------|-------------|-------------------|
| Short Four-Echo | ? | TMOUT -> RST |
| Long Four-Echo LBSY | ? | 放弃或降级 |
| Long Four-Echo TBSY | 0 (no retry) | 立即终止 |

### 流水线 Flush 条件

| Trigger | Scope | Description |
|---------|-------|-------------|
| RST asserted | Full pipeline | 立即清空所有阶段 |
| Retire fault | Current instruction | 清除当前指令及后续 |
| CU protocol error | Related stages | 清除涉及阶段 |

#### [cfg.ip]

- 硬件清零：复位时
